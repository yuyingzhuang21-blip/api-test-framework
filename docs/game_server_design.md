# 模拟游戏服务器 设计稿 v0.2

> 目标：为 API 测试框架提供**可控、可复现**的靶场，让测试从"测公网练习网站"升级为"测游戏业务接口"。
> 原则：本地运行、内存存储（重启即重置）、无外部依赖、规则简单但贴近真实游戏。

## 决策记录

| # | 决策点 | 结论 |
| --- | --- | --- |
| 1 | 账号体系 | **预置账号 + 注册接口**（两者都要） |
| 2 | 保底机制 | **软保底（概率递增）+ 硬保底（90 抽必出）** |
| 3 | 抽卡消耗 | 消耗钻石 |
| 4 | 抽卡历史接口 | 保留 |
| 5 | 排行榜数据来源 | **方案 B**：预置数据兜底 + 追加 `POST /api/score/submit` |
| 6 | 是否植入缺陷 | 暂不植入，后续作为可选进阶练习 |

## 一、技术选型

- FastAPI + uvicorn
- 单文件起步：`game_server.py`（后续可按路由拆分）
- 数据存内存字典：`PLAYERS`、`TOKENS`、`INVENTORY`、`RANKING`、`GACHA_HISTORY`
- 启动：`uvicorn game_server:app --port 8000`
- 自检入口：浏览器打开 `http://127.0.0.1:8000/docs`（FastAPI 自动生成的交互式文档）

## 二、接口清单

### 1. 注册

`POST /api/register`
请求：`{ "username": "newplayer", "password": "abc123" }`

| 场景 | 响应 |
| --- | --- |
| 成功 | 201 `{"code": 0, "data": {"uid": 1003, "username": "newplayer", "gems": 16000}}` |
| 用户名已存在 | 400 `{"code": 4010, "msg": "用户名已存在"}` |
| 用户名长度不在 3~12 | 400 `{"code": 4011, "msg": "用户名长度需为 3~12 位"}` |
| 密码长度 < 6 | 400 `{"code": 4012, "msg": "密码长度不能少于 6 位"}` |

规则：新用户赠送 16000 钻石（保证可测抽卡）；预置账号 `player1 / 123456`、`player2 / 123456`。

### 2. 登录

`POST /api/login`
请求：`{ "username": "player1", "password": "123456" }`
响应 200：

```json
{ "code": 0, "data": { "uid": 1001, "username": "player1", "token": "tk_xxx", "gold": 50000, "gems": 16000 } }
```

| 场景 | 响应 |
| --- | --- |
| 密码错误 | 401 `{"code": 4001, "msg": "用户名或密码错误"}` |
| 用户名为空 | 400 `{"code": 4002, "msg": "用户名不能为空"}` |
| 重复登录 | 200，签发新 token，旧 token 失效 |

### 3. 抽卡（核心接口）

`POST /api/gacha/draw`
请求头：`Authorization: Bearer <token>`
请求体：`{ "times": 1 }` 或 `{ "times": 10 }`
响应 200：

```json
{
  "code": 0,
  "data": {
    "results": [ { "item_id": "C1001", "name": "星穹剑", "rarity": 5, "is_new": true } ],
    "pity_after": 1,
    "gems_after": 15840
  }
}
```

业务规则：

1. 消耗：单抽 160 钻石，十连 1600 钻石
2. 出货概率（软保底）：基础 5 星 0.6%、4 星 5.1%、其余 3 星；
   5 星概率随保底计数递增，函数定义：

   ```python
   def five_star_rate(pity: int) -> float:
       """pity: 距离上次出五星已经抽了多少次"""
       if pity + 1 >= 90:                                    # 硬保底：第 90 抽必出
           return 1.0
       return min(0.006 + max(0, pity - 73) * 0.06, 1.0)     # 74 抽起每抽 +6%
   ```

3. 硬保底：无论概率如何，第 90 抽必出 5 星；出 5 星后计数归零
4. 十连内逐抽结算，保底计数逐抽累加

| 异常场景 | 响应 |
| --- | --- |
| 未带 / 无效 token | 401 `{"code": 4003, "msg": "未登录或凭证失效"}` |
| 钻石不足 | 400 `{"code": 4004, "msg": "钻石不足"}` |
| times 不是 1 或 10 | 400 `{"code": 4005, "msg": "抽卡次数只能是 1 或 10"}` |

### 4. 背包查询

`GET /api/inventory`（需 token）

```json
{ "code": 0, "data": { "items": [ { "item_id": "C1001", "name": "星穹剑", "rarity": 5, "count": 2 } ] } }
```

规则：未获得的物品不出现；空背包返回 `items: []`。

### 5. 物品使用

`POST /api/inventory/use`（需 token）
请求体：`{ "item_id": "C1001", "count": 1 }`

| 场景 | 响应 |
| --- | --- |
| 成功 | 200 `{"code": 0, "data": {"item_id": "C1001", "left": 1}}` |
| 数量不足 | 400 `{"code": 4006, "msg": "物品数量不足"}` |
| 物品不存在 | 400 `{"code": 4007, "msg": "物品不存在"}` |
| count <= 0 | 400 `{"code": 4008, "msg": "使用数量必须大于 0"}` |

### 6. 排行榜

`GET /api/ranking?limit=10`

```json
{ "code": 0, "data": { "list": [ { "rank": 1, "uid": 1001, "username": "player1", "score": 9850 } ] } }
```

规则：按 score 降序；**并列分数取同名次（competition ranking，形如 1、2、2、4）**；`limit` 默认 10，最大 100（超出按 100 处理）；`limit <= 0` → 400 `{"code": 4009, "msg": "limit 参数非法"}`。

分数提交（`POST /api/score/submit`，需 token，请求 `{ "score": 9850 }`）：

- 只保留历史最高分：提交低分不覆盖已有高分
- `score < 0` → 400 `{"code": 4013, "msg": "分数不能为负数"}`
- 玩家首次提交即进入榜单

数据来源（已确定方案 B）：

- 预置：服务器启动时写入 5 条分数记录，保证榜单非空
- 追加 `POST /api/score/submit`（需 token，请求 `{ "score": 9850 }`）：支持"提交分数 → 查询排行榜"完整链路测试

### 7. 抽卡历史

`GET /api/gacha/history?limit=20`（需 token）
返回最近抽卡记录：

```json
[ { "item_id": "C1001", "rarity": 5, "pity_at_draw": 90, "created_at": "2026-09-18T10:00:00" } ]
```

用途：为保底验证提供可断言的侧面证据（抽卡返回只能看结果，历史记录能看到"第几抽出的"）。

## 三、测试要点

| 被测对象 | 用例方向 |
| --- | --- |
| 注册 | 成功、重名、用户名长度边界（2/3/12/13）、密码过短 |
| 登录 | 正常、密码错、空用户名、重复登录后旧 token 是否失效 |
| 抽卡 | 单抽、十连、钻石不足、非法 times、无 token |
| 保底 | 硬保底：连续抽至第 90 抽必定 5 星；出 5 星后计数归零；软保底：高抽数区间出货率显著高于低抽数区间（大样本统计） |
| 背包 | 空背包、使用不存在物品、数量正好用尽、超出数量、count<=0 |
| 排行榜 | 排序正确性、limit 边界（0 / 1 / 100 / 101）、并列分数同名次（1,2,2,4）、提交高分覆盖 / 低分不覆盖 |
| 性能 | 本地接口响应时长断言（可控环境，才是真正有意义的性能测试） |

## 四、实现顺序

1. 骨架：FastAPI 应用 + 注册 + 登录
2. 背包查询 + 物品使用
3. 抽卡（概率 + 软/硬保底 + 抽卡历史）
4. 排行榜（+ 分数提交，视方案 A/B 决定）
5. 接入测试框架：`.env` 增 `GAME_API_BASE_URL`，新增 `clients/game_client.py` + `tests/game/`
